## 1. Види NoSQL баз

NoSQL ("not only SQL") — бази, що відмовляються від частини можливостей реляційної моделі (жорстка схема, JOIN, багатотабличні ACID-транзакції) заради горизонтального масштабування, швидкості певних операцій або зручнішої моделі даних. Більшість розподілених NoSQL систем обирають доступність і стійкість до розділення мережі (AP за теоремою CAP) та модель узгодженості BASE ("в кінцевому підсумку узгоджено") замість ACID, хоча сучасні MongoDB і Redis підтримують і транзакції.

## 2. Чи ефективніше винести частину даних в іншу базу

Розглянемо частини предметної області з лабораторної 1.

Залишаються в PostgreSQL — авто, водії, категорії, закріплення, рейси, ТО, страхування, штрафи, користувачі. Тут важливі саме можливості реляційної СУБД: зовнішні ключі, транзакції через кілька таблиць (старт рейсу змінює рейс і статус авто), тригери-валідатори (категорія водія, пробіг), soft delete і аудит, звіти з JOIN. Обсяг даних малий і стабільний. Перенесення в NoSQL тут нічого не дасть, а цілісність доведеться переносити в код.

Нова вимога — телеметрія з GPS-трекерів. Кожне авто кожні 30 секунд надсилає координати, швидкість і показники датчиків, а трекер фіксує події (різке гальмування, перевищення швидкості, перегрів вантажу в рефрижераторі тощо). Ці дані мають інші властивості, ніж бізнес-дані:

1. **Великий потік запису.** Одне авто — 2 880 точок за добу; автопарк із 500 авто — 1,44 млн точок за добу, і кожна точка має 2–4 показники датчиків. У реляційній моделі це мільйони дрібних рядків з окремим заголовком, ключами і перевіркою зовнішніх ключів.
2. **Дані лише дописуються** і ніколи не змінюються заднім числом, тож транзакції через кілька сутностей не потрібні.
3. **Читаються цілим агрегатом.** Щоб показати рейс на карті, потрібні всі точки, датчики і події одного рейсу. У документній базі це один документ, у SQL — JOIN кількох великих таблиць.
4. **Змінна схема.** Набір датчиків залежить від типу авто: в електромобіля батарея, у вантажівки-рефрижератора температура вантажу і навантаження на вісь, в автобуса пасажири і двері. У SQL це або EAV-таблиця, або багато NULL-колонок, або JSONB. У документі просто є або немає поля.
5. **Геозапити** ("які авто були біля адреси") — у MongoDB вбудований індекс 2dsphere.
6. **Обмеження розміру:** рейс 2–6 годин — це 240–720 точок, тобто приблизно 100 КБ на документ, що набагато менше за ліміт у 16 МБ. Вкладення точок у документ рейсу безпечне.

**Поточний стан, кеш і черги** (де авто зараз, чи онлайн трекер, рейтинг водіїв, черга повідомлень від трекерів) — дані, що живуть недовго і читаються за ключем. Для них природна key-value база в пам'яті, тобто Redis.

**Висновок:** гібридна архітектура. Бізнес-дані залишаються в PostgreSQL, телеметрія виноситься в MongoDB (документ = рейс), оперативний стан — у Redis.

## 3. Реалізація в MongoDB

База fleet_telemetry, колекція tracks. Один документ — один рейс. Авто і водій вбудовані (денормалізовано) з fleet_db, тому для показу рейсу не потрібні звернення до інших сховищ.

```json
{
  "_id": 5,
  "vehicle": { "id": 5, "plate": "AA3001CE", "type": "Truck", "fuel": "Diesel" },
  "driver": { "id": 1, "name": "Shevchenko Andrii Petrovych" },
  "started_at": "2026-06-20T08:45:00Z",
  "ended_at": "2026-06-20T13:30:30Z",
  "summary": { "distance_km": 317.15, "max_speed": 94.9, "avg_speed": 66.5, "points_count": 572 },
  "points": [
    { "seq": 0, "t": "2026-06-20T08:45:00Z",
      "loc": { "type": "Point", "coordinates": [30.770454, 50.531651] },
      "speed": 37.3, "heading": 17,
      "sensors": { "fuel_level": 90.5, "engine_temp": 85.5, "cargo_temp": 4.0, "axle_load": 6.56 } }
  ],
  "events": [
    { "type": "cargo_temp_alarm", "t": "2026-06-20T10:54:30Z",
      "loc": { "type": "Point", "coordinates": [30.63771, 51.348003] }, "severity": 3, "value": 8.05 }
  ]
}
```

Датчики в інших типів авто: електромобіль — `{"battery_soc": 84.5, "battery_temp": 31.7}`, автобус — `{"fuel_level": 76.8, "engine_temp": 95.9, "passengers": 24, "door_open": 0}`.

Індекси (stores/mongo.py): {vehicle.id, started_at}, {driver.id, started_at}, {started_at}, 2dsphere на points.loc (мультиключовий, по всіх точках масиву) і розріджений {points.sensors.cargo_temp} (лише документи рефрижераторів).

Живий трекер дописує точку одним атомарним оновленням: `$push` точки, `$inc` лічильника, `$max` максимальної швидкості, `$set` часу кінця.

Альтернатива для дуже довгих рейсів — шаблон bucket (документ на годину або на 200 точок), щоб документ не ріс без меж. Для рейсів до 6 годин це не потрібно.

## 4. Та сама модель у PostgreSQL

Схема telemetry у базі fleet_db (sql/telemetry.sql). Зовнішні ключі ведуть на fleet.vehicles і fleet.drivers з лабораторної 1 (скрипти в sql/fleet), а пари "авто–водій" для генератора вибираються функцією fleet.fn_driver_can_drive, тобто з урахуванням категорій.

Один документ tracks відображається на 4 таблиці з даними і 2 довідники:

| Частина документа | Таблиця PostgreSQL | Рядків на 2000 рейсів |
|---|---|---|
| _id, vehicle.id, driver.id, часи, summary | telemetry.tracks | 2 000 |
| points[] (час, координати, швидкість, курс) | telemetry.track_points, PK (track_id, seq) | 958 694 |
| points[].sensors{} | telemetry.sensor_readings (EAV), PK (track_id, seq, sensor_type_id) | 2 750 199 |
| events[] | telemetry.track_events | 86 554 |
| назви датчиків і подій | telemetry.sensor_types, telemetry.event_types | 8 + 5 |
| vehicle.\*, driver.\* | fleet.vehicles, fleet.vehicle_models, fleet.vehicle_types, fleet.fuel_types, fleet.drivers (лаб. 1) | — |

Для порівняння додано третій варіант — PostgreSQL JSONB: таблиця telemetry.track_documents, де той самий документ зберігається як jsonb.

Індекси (`sql/telemetry_indexes.sql`) дають ті самі шляхи доступу, що й у MongoDB: B-tree `(vehicle_id, started_at)`, `(driver_id, started_at)`, `(started_at)`; GiST по `ll_to_earth(lat, lon)` (розширення `earthdistance`, сферична відстань, той самий радіус Землі, що і в запитах MongoDB); B-tree `(sensor_type_id, value)` для датчиків; BRIN по часу точок.

## 5. Тестування швидкодії

### Методика

- Однакові дані. Генератор детермінований (seed 42): одна й та сама послідовність рейсів завантажується в усі три сховища в одному процесі. Обсяг — 2 000 рейсів за 180 днів, приблизно 960 тис. GPS-точок, 2,75 млн показників датчиків, 87 тис. подій.
- Однакова перевірка відповіді. Кожен сценарій виконується з однаковими параметрами в усіх рушіях, і програма порівнює результати (множини id, агрегати, кількість точок і подій, суму швидкостей рейсу). Для сценарію запису порівнюється кінцевий стан. В усіх сценаріях результати збіглися, тож порівнюється швидкість однакової роботи.
- Статистика. Спершу прогрівальні запуски, далі сотні запусків для коротких запитів і 5–10 для важких. У таблиці медіана і 95-й процентиль. Масове завантаження (W1) — один прохід.
- Кожен рушій у найкращій розумній формі. Для SQL запити переписувались за планами `EXPLAIN ANALYZE`. Дані завантажуються пакетами по 100 рейсів (COPY у PostgreSQL, insert_many у MongoDB), індекси будуються після завантаження в обох базах.

Сценарії обрано за реальними операціями з телеметрією: масовий запис, живий потік точок, показ рейсу, список рейсів, звіти, геопошук і запит по "гнучкому" полю.

### Аналіз

W1, масовий запис — головна перевага MongoDB. Документ рейсу записується як один BSON-об'єкт, а в SQL той самий рейс — це приблизно 1 900 рядків у чотирьох таблицях. Більшу частину цього часу PostgreSQL витрачає на перевірку зовнішніх ключів: вона виконується окремо для кожного рядка, а sensor_readings посилається на track_points. Без FK PostgreSQL наблизився б до MongoDB, але втратив би гарантію цілісності. Це і є ціна нормалізації на потоці телеметрії. JSONB у PostgreSQL записує один рядок на рейс і тому у 25 разів швидший за нормалізовану схему.

Розмір. 3,8 млн дрібних рядків — це по 23+ байти заголовка на рядок плюс великі індекси (GiST на мільйон точок, PK по трьох полях). Тому нормалізована схема займає 530 МБ проти 70 МБ у MongoDB (WiredTiger стискає дані) і 41 МБ у JSONB (великі значення PostgreSQL стискає в TOAST).

R1, показ рейсу — класичний випадок для документа. MongoDB читає один документ за первинним ключем. PostgreSQL робить 3 запити (шапка з JOIN шести таблиць, точки з LEFT JOIN датчиків, події) і збирає об'єкт у коді. Варіант "одним запитом через json_agg" повільніший: він виконує підзапит датчиків для кожної точки. JSONB займає проміжне місце — потрібно розпакувати TOAST і розібрати JSON.

W2, живий потік — перевага MongoDB. Нормалізована схема на кожну точку виконує в транзакції 5–7 команд (точка, 2–4 показники датчиків, оновлення підсумків рейсу): кожна команда — окреме звернення до бази, а коміт чекає запису WAL на диск. JSONB і MongoDB дописують точку однією командою. Значення jsonb незмінне, тож PostgreSQL щоразу переписує весь документ разом із TOAST, тому JSONB майже вдвічі повільніший за MongoDB. MongoDB оновлює документ атомарним `$push`, але теж переписує його цілком (WiredTiger не змінює документ на місці), тому для дуже довгих рейсів варто розглянути шаблон bucket.

R2, A1, A2, звіти — сильна сторона SQL. Підсумки рейсів у SQL — вузька таблиця на 2 000 рядків, а MongoDB для `$group` по summary мусить прочитати з кешу кожен документ на ~100 КБ (з точками). Для аналітики по окремих точках (A2) MongoDB розгортає масиви через $unwind, а PostgreSQL паралельно сканує вузьку таблицю точок. Якби звіти по точках були головною вимогою, краще підійшла б колонкова база або база часових рядів.

G1, геопошук — однаково, але з важливою знахідкою. Спершу PostgreSQL був тут значно повільнішим, хоча EXPLAIN ANALYZE показував, що сам запит виконується швидко. Причина в тому, що psycopg після п'яти виконань автоматично готує (prepare) запит, а PostgreSQL переходить на загальний (generic) план, який не знає координат пошуку і не використовує GiST-індекс так ефективно. Після plan_cache_mode = force_custom_plan (задано в stores/postgres.py) результат на рівні MongoDB: 2,19 мс проти 2,51 мс. Тобто різниця була в налаштуванні, а не в моделі даних. MongoDB ж дає геопошук "з коробки" одним індексом 2dsphere по масиву точок і відразу повертає документи рейсів.

F1, гнучка схема — перевага MongoDB. Розріджений індекс по points.sensors.cargo_temp містить лише документи рефрижераторів, і MongoDB одразу знаходить потрібні рейси. У SQL датчик зберігається в EAV-таблиці, і перший варіант запиту (JOIN показників із точками) був повільним: планувальник обрав повне сканування 960 тис. точок і hash join. Переписаний запит (спершу min(seq) по показниках, потім пошук точки за PK) — 25,7 мс проти 11,6 мс у MongoDB. За планом помітну частину цього часу займає запуск паралельних worker-процесів, тож з max_parallel_workers_per_gather = 0 запит можна прискорити ще. Отже, SQL може наблизитися до MongoDB, але для цього потрібні EAV, ручна оптимізація запиту і тюнінг сервера, а в MongoDB це просто поле документа і один індекс.

### Висновки

- Телеметрію варто тримати в MongoDB: масовий запис у 62 рази швидший, дописування точки в 10 разів, показ рейсу в 3 рази, гнучкі датчики без EAV, у 7,5 раза менше місця на диску.
- Звіти й агрегації (A1, A2) PostgreSQL рахує у 2–3 рази швидше, список рейсів (R2) — теж швидше, тож їх краще лишити в SQL.
- JSONB — компроміс: компактний і швидкий на читання цілого документа, але на дописуванні поступається MongoDB.
- Геопошук після налаштування планів однаковий: порівняння чесне лише тоді, коли обидві сторони реалізовані якісно.

Обмеження тесту: один вузол без реплікації і шардингу, дані вміщуються в пам'ять, один клієнт, налаштування за замовчуванням. Під паралельним навантаженням від сотень трекерів і з даними, більшими за RAM, співвідношення можуть змінитися.

## 6. Redis — база іншого типу (key-value)

Redis зберігає дані в оперативній пам'яті, і кожна операція виконується за мікросекунди. Значенням ключа може бути не лише рядок, а й хеш, список, множина, впорядкована множина, геоіндекс або потік. У системі автопарку Redis бере на себе оперативні дані, які живуть недовго і читаються за ключем (`telemetry/redis_demo.py`; останні позиції авто беруться з MongoDB, статистика — з PostgreSQL):

| Задача | Структура | Команди |
|---|---|---|
| Поточний стан авто | Hash vehicle:{id}:state | HSET, HGETALL, HINCRBYFLOAT |
| Трекер онлайн? | String з TTL vehicle:{id}:online | SET ... EX 60, TTL, EXISTS (ключ зникає сам, якщо трекер мовчить) |
| Найближчі авто до виклику | Geo fleet:positions | GEOADD, GEOSEARCH ... BYRADIUS ... ASC WITHDIST, GEODIST |
| Рейтинг водіїв за км | Sorted set drivers:km:30d | ZADD, ZINCRBY, ZREVRANGE ... WITHSCORES, ZREVRANK |
| Черга повідомлень від трекерів | Stream telemetry:live | XADD ... MAXLEN ~, XGROUP CREATE, XREADGROUP, XACK, XPENDING |
| Лічильники подій за день | Hash events:{date} | HINCRBY, EXPIRE |
| Кеш звіту з PostgreSQL | String cache:vehicle_stats | cache-aside: GET → промах → запит до v_vehicle_stats → SET ... EX 30 |

Фрагмент виводу (results/redis_demo.txt):

```
> GEOSEARCH fleet:positions FROMLONLAT 30.5234 50.4501 BYRADIUS 150 km ASC COUNT 3 WITHDIST
    AA5001EE    42.22 km
    AA4001MO    54.02 km
    AA3002CE   131.88 km
> ZREVRANGE drivers:km:30d 0 2 WITHSCORES
    Shevchenko Andrii Petrovych        29771.0 km
    ...
miss: 8 rows from PostgreSQL view v_vehicle_stats, saved with SET ... EX 30, 6.40 ms
hit: 8 rows from Redis GET, 0.16 ms
```

Stream telemetry:live з групою споживачів показує, як Redis вписується в архітектуру: трекери пишуть у потік, а воркер групи mongo-writer читає повідомлення, пакетами пише їх у MongoDB і підтверджує через XACK. Непідтверджені повідомлення не губляться — їх видно в XPENDING.

## Запуск

1. Запустити PostgreSQL, MongoDB і Redis:
   ```
   docker compose up -d
   ```
   Під час першого старту PostgreSQL сам створює базу fleet_db зі скриптів sql/fleet і схему telemetry. PostgreSQL лабораторної 2 слухає порт 5433, тому не конфліктує з базою лабораторної 1 на 5432. MongoDB (27017) і Redis (6379) займають свої стандартні порти. Перестворити все з нуля: `docker compose down -v`, потім знову `docker compose up -d`.
2. Встановити застосунок (потрібен Python 3.14+):
   ```
   cd app
   py -3.14 -m venv .venv
   .venv\Scripts\activate
   pip install -e .
   ```
3. Згенерувати і завантажити дані (схема telemetry у fleet_db перестворюється, колекція `tracks` очищається):
   ```
   python -m telemetry load --tracks 2000
   ```
   Для швидкої перевірки підійде `--tracks 200`.
4. Тестування швидкодії — результат у results/benchmark.md:
   ```
   python -m telemetry bench
   ```
   Варіант `--quick` має менше повторів.
5. Демонстрація Redis:
   ```
   python -m telemetry redis-demo
   ```

Рядки підключення за замовчуванням: `host=localhost port=5433 dbname=fleet_db user=postgres password=postgres`, `mongodb://localhost:27017`, `redis://localhost:6379/0`. Їх можна змінити змінними середовища FLEET_DB, FLEET_MONGO, FLEET_REDIS.
